## 一、V2.1 修订目标

V2.1 要解决的不是“再增加多少功能”，而是把 V2.0 中不可判定、不可拒绝、不可回放的条款改成可执行契约。

本版完成后，每一轮施工都必须能回答六个问题：

1. 本轮最小施工切片是什么；
2. 输入真源是什么；
3. 产物 schema 是什么；
4. 至少运行哪些测试；
5. 什么结果算 PASS／PARTIAL／FAIL；
6. 失败后停在哪个状态，允许回退到哪里。

任何一轮不能用“方向正确”“代码已改”“理论上可跑”替代实测证据。

## 三、不可违反的总原则

1. **H5 仍是当前唯一有效正式代际**  
   run：`P0-latch-sync-full-2026-10-30`  
   canonical SHA256：`146b738dd6dd043d620cda89c574b86cb49d0bae0cfaac24f91ddddd38cddcd1`

2. **H5 事实不回填、不重算、不重分类**  
   H5 总数 31,642、data_gap 31,222、draft 420、published 0、blocked 0、schema_invalid 0、gate_pass 31,642、release_eligible 420、去向恒等式差 0，均保持已验收口径。

3. **新能力必须通过新 run 或独立 side-car 输出**  
   不允许修改 H5 或旧 run 来证明新能力。

4. **fail-closed**  
   校验器自身报错、测试未运行但写成通过、关键产物缺失、schema 不合法、真源哈希不一致，一律视为 FAIL。

5. **工程验收与发现质量验收分离**  
   工程 PASS 不证明业务问题一定有效；发现质量六指标在没有业务标注与复核前保持未评。

6. **不宣称全量召回**  
   程序穷尽已完成并锁版（freeze_v2、去向链全落账、六计数闭合）；实体穷尽受④⑤平台表、行为层 enrich 下期、已登记盲区（GAP-009/新老客/变更日志 H1/D4/E1）约束；穷尽对象是指标空间内异常信号，非「所有经营问题」（竞品/商圈地理等数据外维度不在穷尽范围）。详见第十章「穷尽声明」。

7. **不用数据补故事**  
   null 不能用 0 代替；无字段不能编造；无业务核查证据不能升级为“已确认原因”。

8. **不越权施工**  
   每轮只做本施工包授权范围，不顺手重构、不扩角色、不改业务配置、不 commit/push。

## 四、全局 Schema 契约

以下 schema 是 V2.1 后续施工包的最低契约。字段可根据实际情况新增，但不得删除或改变语义。

## 4.1 问题空间节点：`problem_space_node`

```json
{
  "node_id": "PS-L1-E2-001",
  "version": "v1",
  "business_question": "区域补贴前毛利恶化主要由哪些门店和品类贡献",
  "role": "区域总",
  "metric_path": ["E2", "S1", "sales_weight", "avg_sale_price"],
  "dimension_path": ["region", "store", "category"],
  "detection_mechanism": "chain_attribution",
  "input_fields": ["field_a", "field_b"],
  "sample_rule_id": "SAMPLE-28D-30KG",
  "action_owner_role": "区域运营经理",
  "action_template_id": null,
  "current_status": "existing_detector",
  "coverage_bucket": "formal",
  "data_gap_code": null,
  "evidence_level": "numeric_fact",
  "review_status": "approved",
  "review_note": null
}
```

### 状态枚举

`current_status` 只允许：

- `existing_detector`
- `existing_passive_detector`
- `new_detector_candidate`
- `passive_candidate`
- `shadow_candidate`
- `data_gap`
- `excluded`
- `out_of_scope`

`coverage_bucket` 只允许：

- `formal`
- `silent`
- `excluded`

`review_status` 只允许：

- `draft`
- `approved`
- `rejected`
- `deferred`

## 4.2 影响字段：`impact_issue`

```json
{
  "issue_id": "qdm-demo-001",
  "metric_id": "E2",
  "impact_status": "fully_mappable",
  "impact_store_day": 123.4,
  "impact_total": 5678.9,
  "impact_unit": "CNY_per_store_day",
  "impact_basis": "yoy_same_calendar",
  "impact_direction": "negative",
  "business_days_source": "dim_store_calendar",
  "impact_confidence": "recomputed",
  "pool_eligibility": "eligible",
  "not_eligible_reason": null
}
```

### 枚举与规则

`impact_status`：

- `fully_mappable`：可完整映射到当前结果指标，允许进入对应影响池；
- `partially_mappable`：只能部分解释，必须说明缺失部分，不得进入主影响池；
- `not_mappable`：不能量化影响，只能作为诊断线索或数据缺口，不得参与排序。

`impact_confidence`：

- `canonical`：直接来自已验收 canonical；
- `recomputed`：本轮从同一真源重算并可回放；
- `unverified`：字段存在但无法回放或来源不完整。

只有 `fully_mappable + canonical/recomputed` 才允许进入 80% 重点问题池。

## 4.3 去重与父问题抑制：`dedup_suppression`

```json
{
  "issue_id": "qdm-demo-001",
  "dedup_key": "E2|store|SH001|region=华东;category=蔬菜|2026-09|yoy|signal=price_decline",
  "dedup_result": "kept",
  "duplicate_of": null,
  "parent_issue_id": "qdm-parent-001",
  "suppression_result": "not_suppressed",
  "suppression_rule_id": null,
  "suppression_evidence": [],
  "recoverable": true
}
```

### 去重键

```text
dedup_key =
metric_id
+ subject_type
+ subject_id
+ dimension_signature
+ period
+ comparison_basis
+ root_signal_signature
```

### 父问题抑制规则

只有同时满足以下条件，才允许抑制子问题：

1. 子问题期间被父问题期间覆盖；
2. 子问题结果指标可由父问题数值解释；
3. 子问题没有父问题未覆盖的独立切片；
4. 子问题没有父问题未覆盖的独立行动出口；
5. 抑制证据完整可回放。

被抑制问题仍必须保留在 `suppressed_issues` 台账中，不得静默删除。

## 4.4 来源优先级：`source_provenance`

```json
{
  "issue_id": "qdm-demo-001",
  "source_type": "mainline",
  "source_module": "engine.branch_a_mainline",
  "source_priority": 30,
  "shadow_candidate_id": null,
  "related_source_refs": [],
  "promotion_status": null
}
```

### 来源优先级

- `mainline`：30
- `passive`：20
- `promoted_shadow`：10
- `shadow_candidate`：不得生成正式 issue

同一事实只能有一个正式来源。影子候选转正时若与现有正式问题重复，标记 `duplicate_existing`，不得生成新正式问题。

## 4.5 数量去向与原因标签

必须区分三层：

```json
{
  "issue_id": "qdm-demo-001",
  "reason_code": "no_action_exit",
  "accounting_bucket": "data_gap",
  "impact_pool_bucket": "other_excluded"
}
```

### 规则

- `reason_code`：解释为什么没有发布或不能排序，例如 `no_action_exit`、`no_target`、`txn_count_no_source`、`passive_promo_field_missing`；
- `accounting_bucket`：发布数量去向，沿用已验收六计数口径；
- `impact_pool_bucket`：影响池归属，可与发布数量桶不同。

**H5 不回填。**  
876 条 `DATA_GAP:no_action_exit` 在当前 H5 中维持已验收数量口径；在影响池解释中归 `other_excluded`。后续 schema 可以将其原因写成 `reason_code=no_action_exit`，但不得改写 H5 历史计数。

## 4.6 测试契约：`test_case`

```json
{
  "test_id": "G0-H5-SHA-001",
  "phase": "0.1",
  "gate": "G0",
  "test_name": "H5 canonical hash matches registered truth",
  "fixture": "P0-latch-sync-full-2026-10-30/canonical.json",
  "command": "python tools/hash_file.py <canonical_path>",
  "expected": "sha256=146b738dd6dd043d620cda89c574b86cb49d0bae0cfaac24f91ddddd38cddcd1",
  "tolerance": "exact",
  "fail_condition": "hash mismatch or file unreadable",
  "required_evidence": "validation_report.json",
  "blocking_level": "P0"
}
```

### 测试状态

只允许：

- `passed`
- `failed`
- `not_run`
- `blocked`

不得把 `not_run`、`blocked` 写成 `passed`。

## 4.7 阶段闸口报告：`phase_gate_report`

## 五、问题、影响与排序规则

## 5.1 三类问题来源

1. **主线问题**：沿 E2→S1→重量／售价→区域／品类主动下钻的确定性问题。
2. **被动问题**：由旁路信号、行为指标、执行状态、数据完整性检查或沉默空间发现的问题。
3. **影子问题候选**：探索模块或智能体提出、尚未转正的候选。

三者必须统一去重，但影子候选在转正前不进入正式清单。

## 5.2 可排序问题与不可排序线索

不是所有正式记录都必须有核心指标影响值。

- 可排序问题：必须有完整影响字段，才能进入 80% 重点问题池；
- 不可排序线索：允许保留为诊断线索，但必须标记 `impact_status=not_mappable`，不得参与覆盖率和排序；
- 数据缺口：不得用 0 或推测值冒充影响。

## 5.3 影响池入池条件

同一个影响池必须同时满足：

- 同一结果指标；
- 同一父级范围；
- 同一期间；
- 同一比较基准；
- 同一影响单位；
- 根问题无重复或父子重复计算。

E2 与 S1 分池，不得直接相加。

## 5.4 排序规则

第一轮排序固定为：

1. 按核心结果指标影响绝对值降序；
2. 影响完全相同时，才允许使用贡献清晰度、持续性、可行动性做 tie-breaker；
3. 不使用文案热度、角色偏好或主观重要性改序；
4. 若业务未来确认综合权重，必须单独升版、测试和留痕。

## 5.5 80% 萃取

固定顺序：

1. 排除数据和样本不合格记录；
2. 按父级范围、期间、比较基准和影响单位分池；
3. 同事实去重；
4. 父问题抑制；
5. 剩余根问题按影响绝对值降序；
6. 第一条纳入；
7. 未达目标时继续纳入；
8. 首次跨过 80% 的条目纳入后停止；
9. 输出未入选项和实际覆盖率。

必须同时输出：

- 入选清单；
- 未入选清单；
- 累计覆盖率；
- 长尾问题数；
- 净变动解释池；
- 被抑制问题台账。

### R1 对比基准标注铁律（self-explanation，回应"不知道在对比什么"）

- 每个进消息的数字必须带基期标签，标签直接缀在数字后，五选一：
  【同比：去年同期同窗】【环比：前一营业日】【环比：上周同星期X】【达成：月度目标】【贡献：上一级指标总变动】；
- 同一指标首次出现配"口径一句话"（例：毛利日店均＝当日毛利额÷营业店数，元/店·日）；缩写给名词速览，全文统一；
- 每个表格与图形符号给图例出处（判断标准+来源节）；红绿/▲▼ 禁止裸标；
- 冷读者测试：从未看过材料的读者逐数字能回答三个问题——**跟什么比、差多少、在谁的责任范围**，任一条答不出即渲染层返工。

### R2 消息日历骨架三型（回应"周日/月末不确定有无回顾"）

- **普通日**：日报压缩骨架 ①L1+四件套 ③归因链 ⑤下级单元视图 ⑥执行项；
- **周日型＝必有当周回顾段**（缺省即 fail）：本周触发问题台账（新增/持续/已闭环各几条+计数去向勾稽；
  已闭环须指回 issue_id、闭环证据一句话）；**本周无触发也必出零报告句"本周无触发问题"，禁止静默省略**；
- **月末型＝必有当月回顾段**（每月最后一个营业日发）：当月问题台账汇总（触发→确认→行动中→已闭环漏斗+
  数量去向勾稽）、当月累计四件套（累计/当期两行分离）、红队三档当月分布、下月展望（区间值+"按当前斜率"口径）；
- 日历判定以报表日期驱动，与发送日无关；三型骨架写入渲染器，不靠人工记得加。

### R3 业务场景感措辞（回应"业务场景感偏弱"）

- 问题标题句式锁定：**谁·哪天·什么生意环节·差多少**——
  例："西安区 9-22 毛利日店均 8,234 元【环比：周一】−37.2%，差在猪肉售价段"；
- 指标落生意语言：优先 19点前来客（人）、店日均（元）、进货重量（kg）、损耗率（%）；S1/E2 代码只作括号内标注不作主语；
- 每角色段必有"这对我意味着什么"一句（So What 按角色本地化，不写全局空话）。

### R4 拆解结构稳定性铁律（回应"下降都不稳定"——用户澄清：指拆解结构发生漂移）

- 同一角色视图的拆解骨架**锁进渲染器模板，不随当日数据漂移**：层级固定 L1→L2→L3→L4→L5；

- 排序可随数据变（按贡献 pp 降序），结构不可变；
- 结构变更只能随规范版本升级走（v5→v6 评审后），不允许日常渲染"今天这样明天那样"；

- 问题卡固定结构：**判断句标题**（区域/品类·指标·差幅·贡献 pp·合占比例）+ **一句话实质归因**
  （判断句式、说机制不说现象："平均采购价跌 17% 原样让到终端，每人多买 11% 重量但买的人没变多"）+ 四件套 + 展开块；
- 展开块固定五块按数据可得性出现、不得跳序：量价与客单 / 价格链五段 / 让利与折让 / 毛利两段 / 行为
  （损耗率，轮次九解禁后启用，未解禁标缺口）；每块给 pp 贡献+合占比例，跨块对平（v4 纪律沿用）；
- 归因链逐级下钻 L1→L2→L3→L4→L5，每级一句话解释；级间跳钻即 fail；
- 深度参照系：品类卡深度对标 Q3 拆解大分类卡（量价/价格链/让利/毛利四块全）；网格深度对标 MTD 格三行。

### R8 执行项结构（锚定经分会资料目标→举措→执行→效果→根因链）

- 每条执行项带三要素：【目标/举措（引用经分会当月目标或写明新提议）·量化判断标准·时限】；
  只写"待办"无三要素的执行项 fail；
- 问题卡附"根因状态"一行：已确认原因（附证据）/ 诊断线索（附假设编号）/ 待排查（附缺什么数据）——
  对应证据三级分级，禁止把量价贡献对平直接写成业务根因（V1.1 §3.8）。

### v5 新增一票否决项（渲染层 fail-closed，任一即返工）

数字无基期标签；周日/月末消息缺回顾段（含零报告句）；区总页无品类矩阵；运营经理页平铺门店或缺督导组层；
纯门店编码成段；归因跳级或问题卡缺一句话实质归因；执行项缺三要素；图例/缩略语无出处。
**v5 + v5.1 为当前唯一有效渲染细则；v4 仅作历史版本留痕，不与当前施工包并存。**
